# ADR-0004：超长图与大图解码策略

- 状态：Accepted（2026-09-20）
- 依据：解析内存模型 + JVM 预算测试（见第 3 节）；设备实测按用户决定推迟，作为 Stage 0 退出门禁（见第 6 节）
- 日期：2026-09-20
- 相关：ADR-0001（模块边界）、`docs/STATUS.md` S0-05、S0-06

## 1. 上下文

漫画页面的图片形态与常规 App 图片完全不同：

- 单页分辨率高：常见 1000 至 2000 px 宽，高清源可达 3000 px 以上。
- 存在超长条图：宽高比可能达到 1:10 甚至 1:20，解码后单张位图可达数十 MiB。
- 阅读器需要在连续滚动、翻页、双指缩放、旋转和进程恢复中保持可用。
- 预取会在短时间内同时持有多个页面的位图，峰值内存等于“单页成本 × 同时存活页数”。

S0-05 交付的阅读器只渲染页面描述符，不解码任何像素。因此“大图能否在 Compose 中直接用”仍是无证据的假设，它同时决定：

- 是否需要子采样（region/tiling）解码；
- Coil 这类通用图片库能否直接承担漫画页解码；
- 预取窗口可以开多大。

按 ADR-0001 与 `AGENTS.md`，引入新的图片主框架必须先写 ADR，不允许先加依赖再补文档。

## 2. 决策

### 2.1 默认策略：区域/分块解码，整页采样只作对照

S0-06 在 `:feature:reader` 内引入 `PageImageDecoder` 抽象，实现两种策略，并把 `Region` 作为默认：

| 策略 | 实现 | 语义 | 定位 |
| --- | --- | --- | --- |
| `Region` | `BitmapRegionDecoder` + 瓦片/开窗 + 预算采样 | 只解码可见区域，解码字节数与屏幕成正比 | 默认 |
| `Sampled` | `BitmapFactory` + `inSampleSize` | 整页解码后降采样，等价通用图片库 fit 采样 | 对照基线，也是短页快路径 |

**在 S0-06 的实测数据补齐之前不引入 Coil。** 理由：

- 需要回答的正是“通用 fit 采样够不够”，引入 Coil 只会让基线和结论耦合到第三方实现；
- Coil 不承担超长图区域解码，无论结论如何，漫画页解码都需要自有实现；
- 提前锁定图片主框架会压缩 S1-05 的选择空间。

Coil 若按 S1-05 引入，其职责限定为：网络获取、内存/磁盘缓存、跨页面占位与变换；超长图的区域解码仍由自有解码器接管，Coil 不作为超长图的解码路径。此约束在 S1-05 生效时同步更新本 ADR。

### 2.2 位图不进入 UI 状态

- `ReaderUiState`、SavedStateHandle、数据库均不持有 `Bitmap`。
- 解码结果存活在**有界 LRU 字节预算缓存**中，UI 只持有组合作用域内的引用，组合销毁即释放。
- 缓存按 `Bitmap.allocationByteCount` 记账并按 LRU 驱逐；**不调用 `Bitmap.recycle()`**，避免仍在绘制的位图被回收导致崩溃。
- 解码请求必须携带目标尺寸，禁止“按原尺寸整页解码后交给 Compose 缩放”。

### 2.3 内存上界与采样规则

单次解码的硬上界：`PageTiling.DEFAULT_DECODE_BUDGET_BYTES = 24 MiB`（约 2.9 个 1080×2000 视口），由 `PageDecodeBudgetTest` 断言。

计划规则：

1. **整页优先**：若整页在“按显示尺寸采样”后仍在预算内，且所需 `inSampleSize ≤ 2`，则整页作为一个瓦片解码。切分一个本来就放得下的页面只会带来接缝和重复解码。
2. **连续阅读**：否则按宽度贴合，切成不超过 1.5 屏高的瓦片，瓦片在源图坐标下连续且无重叠。
3. **翻页阅读**：否则解码以当前平移位置为中心的窗口（视口 × 1.5 overscan），缩放提高尺度时窗口映射的源像素减少，而不是把小位图放大。
4. **采样取值**：`inSampleSize = max(不模糊的保守值, 满足预算的最小 2 的幂)`。保守值保证解码分辨率不低于显示分辨率；预算值保证内存上界。两者冲突时**预算优先**，代价是最多约 1.41 倍的 GPU 放大。

第 4 条是本次新增的关键规则。中等缩放区间（显示尺度 ∈ (0.5, 1)）下，保守采样需要 `1/scale²` 倍于视口的像素，2 的幂粒度无法收敛：例如 3000×4000 页面在 1080×2000 视口下缩放到 2 倍时，1.5 overscan 窗口需要 2250×4000 源像素，保守采样要分配 34.3 MiB，超过预算。预算采样把它压到 1125×2000（8.6 MiB），代价是 1.44 倍放大。

### 2.4 可执行阈值

| 指标 | 阈值 | 触发动作 | 验证方式 |
| --- | --- | --- | --- |
| 单次解码字节数 | > 24 MiB | 禁止；由采样/切分规则保证不越界 | `PageDecodeBudgetTest` |
| 整页 `inSampleSize` | > 2 | 放弃整页，改走瓦片/窗口 | `RegionPageImageDecoder.canDecodeWholePage` |
| 连续阅读单瓦片高度 | > 1.5 屏 | 继续切分 | `PageTilingTest` |
| 解码字节数与页面长度 | 必须无关 | 超长图不得整页解码 | `PageDecodeBudgetTest` |
| 单指滚动被消费为拖拽 | 出现即缺陷 | 缩放用 `panZoomLock = true`，缩放激活时才关闭列表滚动 | 人工验证（第 6 节） |
| 单页解码耗时 | > 100 ms | 限制预取并发 | 设备实测（第 6 节） |

### 2.5 测试图片必须可生成、可复现

- 只允许仓库内生成的确定性图片，禁止提交任何受版权保护的漫画页。
- 生成器输出尺寸与格式固定，重复执行结果一致。
- 生成的图片不入库；从干净克隆构建时不存在，因此不会进入 Release 包。

## 3. 依据

解码内存是算术，不是观测：

```text
decodedBytes = width * height * 4           （ARGB_8888）
```

因此“这份计划放不放得下”由计划本身决定，可以在 JVM 上断言。`PageTiling` 提供纯函数记账，`PageDecodeBudgetTest` 把上面所有阈值变成可执行断言；`SampledPageImageDecoder`、`RegionPageImageDecoder` 与测试共用同一套计算，避免实现与结论漂移。

1080×2000 视口、24 MiB 预算下的解析结果：

| 页面 | 整页 ARGB_8888 | 整页 fit 采样后 | 实际解码（Region 规则） |
| --- | --- | --- | --- |
| 1080×1440 常见页 | 5.9 MiB | 5.9 MiB | 5.9 MiB，整页不切分 |
| 1920×1080 横向页 | 7.9 MiB | 7.9 MiB | 7.9 MiB，整页不切分 |
| 1080×6000 长条 | 24.7 MiB | 24.7 MiB（超预算） | 12.4 MiB × 2 瓦片 |
| 1080×16000 超长条 | 65.9 MiB | 65.9 MiB（超预算 2.7 倍） | 12.4 MiB × 6 瓦片 |
| 3000×4000 高清 | 45.8 MiB | 11.4 MiB（sample 2） | 11.4 MiB，整页不切分 |
| 1080×64000 合成极端页 | 263.7 MiB | 263.7 MiB | 12.4 MiB × 22 瓦片，与 16000 高时相同 |

由此得到的结论：

- 整页解码的成本随页面长度线性增长，超长条图必然越界；区域解码的成本与页面长度**无关**，这是选择 `Region` 作为默认的根本原因。
- 常见页与高清页在预算内可以整页解码，因此不需要为所有页面引入切分代价。
- 只有“窄而极长”的页面会真正触发切分，切分路径是少数派路径，但必须存在。

## 4. 后果

正面：

- 阅读器原型具备真实解码能力，结论由可执行断言支撑，而不是“在某台设备上看起来还行”。
- 内存上界与设备无关，换机型不需要重新论证策略。
- 解码策略是可替换实现，S1-05 引入 `:core:image` 时只需迁移代码，不需要改 UI 契约。
- 有界缓存让预取窗口可以量化调优。

负面与代价：

- 原型阶段解码代码位于 `:feature:reader`，与 ADR-0001 的“图片管线属于 core”不一致；S1-05 建立 `:core:image` 时必须迁移，本 ADR 记录该债务。
- 中等缩放区间会放弃部分清晰度（最多约 1.41 倍放大），这是内存上界的代价；若设备实测显示该区间观感不可接受，需要在本 ADR 中改规则而不是改实现。
- 翻页缩放时窗口随平移变化，首次实现没有瓦片缓存与超扫描复用，可能出现重复解码；解码耗时数据仍待设备验证。
- 不引入 Coil 意味着原型阶段没有磁盘缓存，重复打开同一页会重复解码文件。
- 解析记账用的是 ARGB_8888 上界；若后续启用硬件位图或 RGB_565，实际占用更低，但本 ADR 的阈值不做下调。

## 5. 替代方案

| 方案 | 结论 |
| --- | --- |
| 直接用 Coil `AsyncImage`，交给它处理一切 | 已否决作为**唯一**路径：fit 采样会把超长条图降采样到不可读（1080×16000 在手机视口下会被压到约 135 px 宽），且不做区域解码。仍可能作为网络与缓存层引入。 |
| 按测量结果决定，不先定规则 | 已否决：内存上界是算术结论，不需要设备才能成立；把可推导的结论交给测量只会推迟决策。 |
| 引入现成子采样库（如 subsampling-scale-image-view） | 已否决：它是 View 体系组件，与 Compose 阅读器和 MVI 状态模型冲突，且引入新的维护面。 |
| WebView 渲染页面 | 已否决：失去手势控制、内存控制和与源运行时的二进制通道一致性。 |
| 服务端切图 | 不适用：图片来自第三方漫画源，无法要求对方预处理。 |

## 6. 尚缺的证据（Stage 0 退出门禁）

用户已决定“非必要不做实机测试”，因此以下项目不在 S0-06 执行，改为 **Stage 0 退出（S0-07）前必须完成的门禁**。
在补齐之前，本 ADR 的第 2.4 节中标注为“设备实测”的行视为未验证，不得写成已验证。

- 测试设备与系统版本、视口尺寸。
- 各 fixture × 策略 × 模式（连续 / 翻页 × zoom 1 与 3）的解码耗时、位图字节数与 PSS 增量，用于校验解析上界与实际分配的偏差。
- 预取窗口 1/2/3 的峰值内存与掉帧。
- 快速滚动、连续翻页、旋转、后台恢复的人工验证。
- 双指缩放与滚动手势冲突的人工验证（阈值已定，行为待确认）。

采集入口已就绪：`LargeImageProbeTest` + `tools/test-images`，命令见 `docs/STATUS.md`。
若实测与第 2.3 / 2.4 节冲突，先更新本 ADR 再改代码。
